- Data-last tests use `pipe` (matches real-world usage)
- Prefer one `expect` per `test` block: failures should pinpoint the exact case
- Keep tests simple and short; more tests are better than tests that do more
- Tests are self-contained: inline every helper; the only shared ones are the modules in `test/` (such as `forceFusion`)
- Use Remeda's own utilities in tests when applicable (`prop`, `constant`, etc.)
- On an array, lazy-only behavior (the items processed so far as `data`, the sentinel, item-by-item call order) exists only in a fused run. `pipe` fuses a run only when one of its functions can end the iteration early; otherwise each function runs its data-first implementation and gets the whole array. Put `forceFusion()` (`test/forceFusion.ts`) in the run, `pipe([1, 2, 3], forceFusion(), forEach(callback))`: it is a pass-through step marked as able to end the iteration, and it throws when its run doesn't fuse
- Lazy callbacks: verify the callback receives the items processed so far with a `vi.fn<LazyCallback<unknown[], unknown>>` mock that returns `[...data]`, asserted per call with `toHaveNthReturnedWith`. The spread is load-bearing: `pipe` reuses one `data` buffer, so asserting on the reference after the pipe finishes compares the mutated, complete array and passes for the wrong reason. Template: `provides the items processed so far to the callback` in `forEach.test.ts`
- A lazy-callback mock whose call arguments are asserted on must declare every parameter up to `data` (`(value, index, data) => ...`, one more for `mapWithFeedback` and `zipWith`) or be a bare `vi.fn()` (`length` 0), so it receives the real items. When evaluated lazily (a fused run, or a non-array input), a shorter mock receives `UNEXPECTED_ACCESS_SENTINEL` as `data` (and, in `map`, the pipe's slot as a 4th argument); comparing the sentinel to an array, or printing it in a failed assertion's diff, throws its `Remeda: ...` error.
